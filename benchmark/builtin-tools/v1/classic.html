omnifeed vs Claude Code built-in WebSearch / WebFetch

40 search queries and 272 sites (four batches), each hit once by each tool, sequentially, on 2026-10-08 from a self-hosted node. Both tools egress from the same French home connection. Latency is the gap between the tool_use and tool_result timestamps in the session transcript (no agent overhead).

Fetch outcomes

For each of the 272 sites: did the tool return what the page shows? Partial means a real page came back but the target fact was missing. Soft-block means a block page was returned as if it were a success. Policy-refused means the built-in fetch refused the domain before sending any request.

Method & caveats

  • Calls were strictly sequential, one tool call per turn, alternating which tool went first. The exceptions are the Wikipedia (batch 1) and go.dev (batch 4) pairs, which ran in parallel by mistake, so their latencies are contaminated.
  • omnifeed fetches used max_chars 0.8–10k (batch 3: 1.5k, batch 4: 800) to limit token cost, so "partial" on a long page (Wikipedia, Le Monde, HF) can mean the fact sat past that window. Total page size is shown in the notes.
  • The built-in WebFetch returns a small-model answer (~200–600 chars), not the page. That is a huge token saving, but it's lossy: it misquoted HN, called MDN an "error page", and the built-in WebSearch summary gave a stale Pi price.
  • omnifeed's time_range, site and language options were used where they're the natural fit. The built-in has allowed_domains but no time or language filter.
  • Single run, n=1 per site and tool. No retries on omnifeed "retryable" errors (IMDb, PDF), to keep load low as requested.
