omnifeed vs Claude Code built-in WebSearch / WebFetch

40 search queries and 272 sites (four batches), each hit once by each tool, sequentially, on 2026-10-09 from a self-hosted node, paced to stay under rate limits. Both tools egress from the same French home connection. Latency is the gap between the tool_use and tool_result timestamps in the session transcript (no agent overhead).

Fetch outcomes

For each of the 272 sites: did the tool return what the page shows? Partial means a real page came back but the target fact was missing. Soft-block means a block page was returned as if it were a success. Policy-refused means the built-in fetch refused the domain before sending any request.

Router simulator: what if an agent used both?

Every strategy replayed over the 272 measured sites. A fallback only fires on a failure the agent can see: built-in failures are always explicit, but omnifeed's silent failures look like success, so today they block the fallback and hand the agent wrong content. Latency of a fallback = first call + second call.

What changed since v1

Same site, same arguments, one day apart. Fixed and regressed count only real changes: the usable / not-usable status flipped, a silent failure became an explicit error (or back), or the run notes record an observed change. A success ↔ partial difference on an unchanged page is a regrade (the grader read the window differently) and is hidden unless you ask for it.

Method & caveats

  • v2 re-ran v1's exact inputs on 2026-10-09 against omnifeed v0.35.0 (crawl4ai 0.9.4, SearXNG 2026.10.4). Calls were strictly sequential, omnifeed first, then the built-in. Two calls ran in parallel by mistake (search S1 and the SwiftUI docs fetch); their notes flag the latency.
  • The run was paced to stay under rate limits: about two fetches a minute, one search every 3 minutes, then every 6 once Google's engine went silent at 15:43 UTC. Google stayed silent for the rest of the run, so later omnifeed searches ran on privacywall, yandex and braveapi only. The block log above has the details.
  • omnifeed fetches used max_chars 0.8–10k, as in v1, so "partial" on a long page can mean the fact sat past that window. Total page size is in the notes.
  • The built-in WebFetch returns a small-model answer, not the page: a big token saving, but lossy (it misread a search page as a block page and called CoinGecko a "block page" while describing it).
  • Both tools egress from the same IP. When Google flagged it (Scholar /sorry at 15:48), it flagged both.
  • Single run, n=1 per site and tool. A transport reset (ECONNRESET) between the client and an MCP server was retried once; nothing else was retried.
